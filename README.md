# StackWatch 2.0

Мониторинг серверов Linux и Windows: HTTP/HTTPS, TCP-порты, метрики агента, графики и инциденты. Проверки работают в отдельном процессе независимо от открытой вкладки.

[Приватный репозиторий StackWatch](https://github.com/Kirill-DevSecOps/StackWatch).

При обновлении сохранены совместимые имена базы `pulsewatch.sqlite`, служб и томов Docker, чтобы использовать накопленные данные. Название в интерфейсе, уведомлениях и документации — StackWatch.

## Разработка и Git

Каждое завершённое изменение фиксируется отдельным коммитом после подходящей проверки. При настроенном удалённом репозитории коммиты отправляются туда. Правило для будущей работы сохранено в `AGENTS.md`.

Базы данных, токены, рабочие `.env`, адреса серверов и резервные копии остаются локальными. В репозитории хранятся исходники, инструкции, тесты и примеры настроек. Для упаковки исходников без этих данных и без истории `.git` используйте `pwsh -File deploy/package.ps1` (PowerShell 7).

## Быстрый запуск

Нужен **Node.js 24+**. Сторонние npm-пакеты не требуются.

Получение исходников при наличии доступа к приватному репозиторию:

```sh
git clone https://github.com/Kirill-DevSecOps/StackWatch.git
cd StackWatch
```

```sh
npm start
```

На Windows также можно запустить `start.cmd`. Откройте **http://127.0.0.1:4310**, нажмите «Добавить сервер» и укажите свои адреса. Для непрерывного мониторинга процесс и компьютер должны оставаться включёнными.

Демо включается отдельно и явно помечено. Примерные адреса не проверяются, примерные графики не сохраняются. При переходе к настройкам демо выключается, поскольку настройки относятся к реальному приложению.

## Шесть улучшений версии 2

1. **Telegram:** настройки в панели, сообщение о сбое и его причине, длительности, восстановлении, напоминания, тест по кнопке и журнал доставки.
2. **Графики за 24 часа и 7 дней:** отклик, CPU, память, диск; среднее и максимум, таблица значений, реальные пропуски данных.
3. **Живые карточки:** открытая карточка автоматически обновляется каждые 5 секунд, включая метрики, графики и последние проверки.
4. **Точные тревоги:** подтверждение сбоя и восстановления, выдержка времени для перегрузки, разовые и еженедельные техработы, напоминания до принятия инцидента.
5. **Комплект для домена:** Docker Compose + Caddy, HTTPS и продление сертификатов, автозапуск, постоянные тома, автоматические проверенные резервные копии и восстановление.
6. **Независимый наблюдатель:** отдельный `watchdog.mjs` обнаруживает отказ самой службы и отправляет уведомления через собственный Telegram/webhook.

В локальной сборке всё реализовано, но Telegram требует ваших реквизитов бота и чата. Домен, выпуск настоящего сертификата и независимый наблюдатель активируются после установки на ваших серверах.

## Типы проверок

| Тип | Ввод | Результат |
| --- | --- | --- |
| HTTP / HTTPS | Полный URL, например `https://your-server/health` | Ожидаемый HTTP-код, задержка до заголовков, ошибки DNS/сети/TLS, срок сертификата |
| TCP | IP/домен и отдельный порт | Доступность TCP-порта и время подключения |
| Агент | URL `/health` и токен | Доступность, CPU, память, заполнение выбранного диска |

HTTP ожидает точный код (по умолчанию 200) и не следует редиректам. Укажите конечный URL либо измените ожидаемый код. TCP 22 или 3389 проверяет открытый порт SSH/RDP, но не работоспособность приложения. Для prod добавляйте health/readiness-проверку приложения; можно создать несколько проверок для одного сервера.

Проверка TLS включена. Для внутреннего центра сертификации используйте `NODE_EXTRA_CA_CERTS`; отключать проверку сертификата не нужно.

### Подключение агента Linux / Windows

**Linux с входом root по паролю, мониторинг с Windows:** запустите `connect-linux.cmd` и укажите адрес сервера. Если есть локальный файл `data/connection-default.json` с полями `address` и `user`, мастер использует его; этот файл не попадает в Git и архив исходников. Пароль вводится в отдельном SSH-окне и не сохраняется. При первом входе сверьте отпечаток SSH-ключа сервера с данными провайдера. Для адреса из командной строки:

```powershell
node deploy/connect-linux.mjs ВАШ-IP root
```

Мастер рассчитан на Linux с systemd и архитектурой x86_64/aarch64. Он устанавливает службу `pulsewatch-agent`, создаёт случайный токен и отдельного системного пользователя, запускает агент только на `127.0.0.1:9109`. Если подходящего системного Node.js нет, загружает официальный Node.js 24 LTS в `/opt/pulsewatch-agent/runtime` и сверяет SHA-256. Системный Node.js не заменяется. Нужны `curl` либо `wget`, `tar`, `xz`, `sha256sum`; отсутствующие системные утилиты мастер не устанавливает автоматически.

Мастер проверяет метрики и добавляет отдельную проверку в локальную панель. SSH-туннель связывает `127.0.0.1:19109` компьютера с портом агента; серверный порт не публикуется. **Окно подключения и StackWatch должны оставаться открытыми.** После закрытия туннеля метрики станут недоступны, а независимая TCP-проверка SSH продолжит работать. Повторный запуск сохраняет токен и использует существующую проверку. Для переноса мониторинга на постоянный сервер настройте там VPN/HTTPS или постоянный SSH-туннель: адрес `127.0.0.1` относится к машине мониторинга.

Служба на Linux запускается после перезагрузки. Диагностика: `systemctl status pulsewatch-agent` и `journalctl -u pulsewatch-agent -n 30`. Конфигурация с токеном находится в `/etc/pulsewatch-agent.env` с правами 600. SSH-ключи доверенных хостов Windows-мастер хранит в `data/ssh_known_hosts`. Мастер требует работающую локальную панель на порту 4310 без ключа входа; для панели с авторизацией используйте ручное подключение ниже. Устройство [SSH-перенаправления портов описано в документации OpenSSH](https://man.openbsd.org/ssh#L).

На удалённом сервере нужен Node.js 24+. Скопируйте `agent.mjs` и `.env.agent.example`, переименуйте последний в `.env.agent`.

Создайте токен:

```sh
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

В `.env.agent` укажите свой токен и IP защищённого сетевого интерфейса:

```dotenv
AGENT_HOST=10.10.0.12
AGENT_PORT=9109
AGENT_TOKEN=свой-случайный-токен-не-короче-24-символов
```

`10.10.0.12` — пример. По умолчанию агент доступен только на `127.0.0.1`. Запуск:

```sh
node --env-file=.env.agent agent.mjs
```

В панели добавьте тип «Агент», URL `http://10.10.0.12:9109/health` и тот же токен. Для HTTP используйте доверенную VPN/защищённую сеть. Для публичного подключения нужен HTTPS-прокси перед агентом. Ограничьте доступ к порту в брандмауэре машиной мониторинга.

Агент измеряет CPU каждые 2 секунды, физическую память и одну файловую систему. На Linux для памяти используется `MemAvailable`. Для диска задайте `AGENT_DISK_PATH=/var` или `AGENT_DISK_PATH=C:\`; по умолчанию выбирается корневая файловая система/диск рабочей папки. Первые метрики появятся примерно через 2 секунды. При ошибке метрик агент возвращает 503 вместо ложных нулей.

## Как устроены тревоги

Значения по умолчанию можно изменить в параметрах каждого сервера:

| Параметр | Значение |
| --- | --- |
| Интервал после завершения проверки | 30 секунд |
| Таймаут | 5 секунд |
| Ошибок подряд до недоступности | 2 |
| Успехов подряд без предупреждений для восстановления | 2 |
| Непрерывная перегрузка до предупреждения | 60 секунд |
| Напоминание о непринятом открытом инциденте | Каждые 30 минут; 0 выключает |
| Предупреждение по задержке | 800 мс |
| CPU / память / диск | 90% |
| Скорое истечение TLS | Менее 14 дней |

Краткая перегрузка получает статус «Наблюдаем перегрузку». Первая чистая проверка после инцидента — «Проверяем восстановление». Длительная пауза между результатами сбрасывает доказательства непрерывности; старый замер после перезапуска не подтверждает текущую перегрузку. Начало инцидента учитывается с первого наблюдаемого плохого результата, а подтверждение и сообщение происходят после заданного порога.

«Принять» останавливает напоминания. Если серьёзность открытого инцидента меняется, появляется новое событие и требуется новое принятие. Повторение неизменного результата не отправляет одинаковые сообщения на каждой проверке. Изменение параметров, пауза, удаление или начало техработ закрывают инцидент с соответствующей причиной, без ложного сообщения о восстановлении.

### Техработы

В форме сервера откройте «Расписание техработ»:

- **Один раз:** начало и конец в локальном времени браузера, до 31 дня.
- **Еженедельно:** дни, начало, конец и часовой пояс IANA, например `Europe/Moscow`. Переход через полночь поддерживается; ночь относится к дню начала. В дни перевода часов применяется выбранное местное время.

Во время окна результаты и метрики сохраняются; новые тревоги, напоминания и ожидающие в очереди сообщения этой проверки подавляются. Открытый инцидент закрывается с причиной «Техработы». После окончания накопление ошибок начинается заново. Уже переданное получателю сообщение отозвать нельзя.

### Графики и достоверность

Одна точка: 10 минут для суток, 1 час для недели. Сплошная линия — среднее, пунктир — максимум, отдельный пунктир — порог. Нет измерений — разрыв, без дорисовки значений. У HTTP/TCP нет метрик CPU/памяти/диска; графики объясняют, что нужен агент. Под графиками есть таблица значений.

Процент успешных проверок — доля успешных полученных результатов, **не процент времени** доступности. Периоды выключенного мониторинга не превращаются в успехи или сбои. Техработы исключены из этой доли, но видны в истории и графиках. Задержки на графике учитывают только успешные ответы; время неудачной попытки не выдаётся за отклик сервера.

История хранится 7 дней по умолчанию. Открытые инциденты не удаляются при очистке. В общем журнале — до 200 последних инцидентов, сначала открытые. В карточке — последние 60 проверок.

## Telegram

1. Создайте бота через [@BotFather](https://t.me/BotFather) и получите токен.
2. Напишите ему `/start` или добавьте в группу с разрешением отправки сообщений.
3. Узнайте Chat ID из `message.chat.id` входящего события вашего бота (`getUpdates` либо уже настроенный webhook). Не передавайте токен сторонним сайтам.
4. В «Настройках» заполните Telegram, включите отправку и сохраните. Доступен фильтр «Только production».
5. Нажмите «Отправить тест» и проверьте журнал доставки.

Токен не возвращается в API и хранится в базе с AES-256-GCM; ключ — в приватном `data/secrets.key`. Пустое поле при сохранении оставляет токен прежним. Не теряйте файл ключа. Резервные копии содержат его, поэтому тоже являются секретными.

Telegram отправляется прямо через официальный [Bot API / sendMessage](https://core.telegram.org/bots/api#sendmessage). Сообщение содержит сервер, окружение, причину, длительность, начало и время события. У восстановления сохраняется исходная причина сбоя. Запросы не используют HTML/Markdown-форматирование пользовательских названий.

Для каждого канала — отдельная долговечная очередь, до 5 попыток. Ошибка webhook не блокирует Telegram. Учитывается `retry_after` Telegram. После исчерпания попыток доступна ручная кнопка «Повторить». При смене бота/чата ожидающие сообщения прежнему получателю отменяются. Факт доставки отражает принятие сообщения API, а не прочтение человеком. При неопределённом результате сетевой попытки возможен повтор сообщения.

`TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` могут задать начальные настройки при первом запуске новой базы. После этого настройки из панели сохраняются в базе и имеют приоритет.

### Webhook и браузер

Существующий JSON webhook сохраняется. В `.env` задайте `ALERT_WEBHOOK_URL` и при необходимости `ALERT_WEBHOOK_TOKEN`, затем перезапустите приложение. События: `down`, `degraded`, `recovered`, `reminder`. Поля включают `event_id`, `incident_id`, `monitor`, `message`, `cause`, `duration_seconds`, `started_at`, `timestamp`. Используйте `event_id` для устранения повторов у получателя.

Звук и системные уведомления браузера действуют при открытой панели и требуют разрешения/взаимодействия с браузером. Для закрытой вкладки используйте Telegram или webhook. По умолчанию внешние каналы выключены и никому не отправляют сообщения.

## Домен, HTTPS и автозапуск

Полная инструкция доступна из настроек или по адресу `/guide.html` в панели. Требуются ваш сервер, Node.js 24+, Docker с Compose и домен. Размещайте мониторинг отдельно от prod.

1. Перенесите приложение на сервер.
2. Укажите IP сервера в DNS A-записи. Если есть AAAA, проверьте также IPv6.
3. Освободите и откройте входящие TCP 80/443. Разрешите серверу исходящий доступ для сертификатов, мониторинга и Telegram.
4. Из папки приложения выполните:

```sh
node deploy/setup.mjs monitor.example.com --start
```

Замените домен своим. Создаётся `.env.production` со случайными независимыми `ACCESS_KEY` и `HEALTH_TOKEN`. Ключ входа смотрите в файле; он не выводится в лог. Повторно существующий файл не перезаписывается. Без `--start` скрипт только создаёт настройки.

Для повторного запуска, обновления и логов:

```sh
docker compose --env-file .env.production -f compose.production.yaml up -d --build
docker compose --env-file .env.production -f compose.production.yaml logs -f
```

Caddy получает и продлевает сертификат, перенаправляет HTTP на HTTPS. Приложение доступно только внутри Docker-сети, наружу публикуются 80/443. Данные и сертификаты находятся в постоянных именованных томах. Успешный выпуск сертификата требует корректного DNS и сетевого доступа: [Automatic HTTPS](https://caddyserver.com/docs/automatic-https).

### Перенос уже подключённых серверов

Создайте копию в локальной панели и перенесите каталог этой копии на сервер. Подготовьте `.env.production` без `--start`. До первого запуска восстановите копию в пустой том, заменив `/absolute/backup` абсолютным путём к скопированному каталогу:

```sh
docker compose --env-file .env.production -f compose.production.yaml build pulsewatch
docker compose --env-file .env.production -f compose.production.yaml run --rm --no-deps --user 0:0 -v /absolute/backup:/restore:ro pulsewatch sh -c 'node deploy/restore.mjs /restore /app/data && chown -R node:node /app/data'
docker compose --env-file .env.production -f compose.production.yaml up -d
```

Восстановление требует пустого тома и не затирает действующие данные. Одноразовая команда выполняется от root, чтобы прочитать приватную копию, затем передаёт восстановленные файлы пользователю node; основная служба продолжает работать от node. В Windows заключите аргумент пути тома в кавычки при наличии пробелов. Ключ доступа к панели берётся из новой `.env.production`; токен Telegram и серверы восстанавливаются из базы.

### Без Docker

Для локального/сетевого запуска скопируйте `.env.example` в `.env`. При сетевом доступе обязательны `HOST`, длинный `ACCESS_KEY` и точный `PUBLIC_ORIGIN` без завершающего `/`. Для HTTPS настройте свой прокси, сохраняющий Host; приложение проверяет его и Origin запросов изменения.

Linux: используйте `pulsewatch.service`, пользователя `pulsewatch`, каталог `/opt/pulsewatch`; проверьте путь Node.js в unit-файле и права на папку данных. Затем от администратора:

```sh
sudo cp /opt/pulsewatch/pulsewatch.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now pulsewatch
```

Windows: в Планировщике заданий задайте запуск `node.exe` с аргументами `--env-file-if-exists=.env server.mjs`, рабочую папку приложения, запуск при включении компьютера и повтор после ошибки. Разрешите работу независимо от входа пользователя, отключите ограничение длительности и запретите второй экземпляр.

## Внешний наблюдатель

Наблюдатель запускается **на другой машине**, которая не зависит от StackWatch и prod. Он не запускается автоматически на том же компьютере: это не защитило бы от отказа компьютера.

1. В настройках основной панели получите адрес `/healthz` и отдельный ключ наблюдателя. Этот ключ не даёт административный доступ.
2. На второй машине скопируйте приложение, создайте `.env.watchdog` из `.env.watchdog.example`.
3. Заполните `WATCHDOG_URL`, `WATCHDOG_TOKEN`, Telegram-токен/Chat ID либо webhook. Получатель настраивается на второй машине независимо от основной базы.
4. Запустите:

```sh
docker compose -f compose.watchdog.yaml up -d --build
```

Без Docker: `npm run watchdog`, с автозапуском через systemd или Планировщик заданий.

Проверка каждые 30 секунд, таймаут 5 секунд, отказ после 3 ошибок, восстановление после 2 успехов. Повторное напоминание каждые 30 минут. Состояние и очередь сохраняются в `watchdog-data`; до 5 попыток доставки, ошибки видны в логах. Сам наблюдатель требует постоянно работающего процесса и собственного доступа к сети/каналу уведомлений. Для его отказа абсолютной гарантии нет; основная панель показывает отсутствие его запросов, пока доступна.

`/healthz` проверяет цикл планировщика и просроченные проверки; работающий HTTP-сокет при зависших проверках не выдаётся за исправный мониторинг. Сбой наблюдаемого prod не делает сам StackWatch неисправным. Данные о серверах и административные настройки через `/healthz` не раскрываются. Встроенный Docker healthcheck не выдаётся за внешнего наблюдателя. Системные часы обеих машин должны быть синхронизированы.

## Резервные копии

Копия создаётся при первом запуске и затем каждые 24 часа. По умолчанию сохраняются 7 успешных копий. В настройках доступны состояние, ошибка и ручной запуск. SQLite копируется согласованно во время работы с помощью встроенного API и проверяется через `quick_check`.

Состав: `pulsewatch.sqlite`, `secrets.key`, `health.key` (если используется), `runtime-settings.json`, `manifest.json`. В runtime-настройках есть секретные параметры запуска; доступ к копиям нужно ограничить. На Unix создаются приватные права; на Windows используйте ACL папки.

Настройки среды: `BACKUP_HOURS` (1–168), `BACKUP_KEEP` (1–30), `BACKUP_DIR` (по умолчанию `data/backups`). Сохраняйте копии отдельно от диска мониторинга. В Docker можно выгрузить их:

```sh
docker compose --env-file .env.production -f compose.production.yaml cp pulsewatch:/app/data/backups ./saved-backups
```

Восстановление в новый пустой каталог:

```sh
node deploy/restore.mjs ./saved-backups/backup-ИМЯ ./restored-data
```

Проверьте runtime-настройки из копии, задайте `DATA_DIR` этим каталогом и запустите службу. Действующий процесс перед переключением нужно остановить. Файл `.env` скрипт не перезаписывает.

## Обновление с версии 1

Схема базы расширяется автоматически; адреса, конфигурация и история сохраняются. Сначала сохраните резервную копию предыдущей версии. Новые параметры старых проверок получают стандартные значения: 2 успеха для восстановления, 60 секунд перегрузки, напоминание каждые 30 минут. Настройте их при необходимости.

Старые токены агентов остаются в локальной базе в прежнем формате. Шифрование версии 2 относится к Telegram. Только один экземпляр приложения должен работать с одним каталогом данных.

## Проверка и ограничения

```sh
npm test
```

Автотесты проверяют HTTP/TCP, таймауты и метрики агента, миграцию v1, подтверждение тревог и восстановления, техработы и часовые пояса, напоминания, агрегирование графиков, шифрование Telegram, контракт sendMessage на подменном получателе, независимые очереди, восстановление резервной копии, watchdog при отказе основного сервиса и защиту API. Внешние сообщения во время тестов не отправляются.

В этой среде проверены Windows/Node.js 24, интерфейс и конфигурации Compose. Производственный Docker-стек, настоящий DNS/TLS, отправка реальному Telegram-боту и размещение на двух физических машинах требуют ваших серверов и реквизитов; они не объявляются подключёнными локальными тестами.

До 100 проверок, до 8 одновременных запросов. При большой очереди медленных серверов фактический интервал растёт. Нет автоматического исправления prod, SNMP/ICMP, отдельных пользовательских ролей и высокой доступности основного сервиса. Все вошедшие пользователи являются администраторами. Проверяются только адреса, доступные машине мониторинга; `localhost` внутри контейнера означает сам контейнер.
